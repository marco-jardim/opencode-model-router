## S1 — Agent registered without a model, per-call `model: provider/model#variant`

**Question.** If a role agent is registered with no `model`, which model and which effort/variant reach the provider when the parent dispatches it with a per-call `model`, for an Anthropic and for an OpenAI-Responses provider? And with no per-call model — does it take the parent session's model or the host default?

**Method.** Test `S1 agent registered without a model …` (lines 148–198). The agent comes from `hostConfig.agents` (`agentWithoutModel()`); the test reads the generated `opencode.json` and `client.agent.list()`, then dispatches four times from one root. The root runs on `anthropic/claude-opus-5-5#medium`, a model and variant that no dispatch asks for (the per-call models are `sonnet#medium`, `opus#xhigh` and `luna#high`) and that is not the host default (`anthropic/claude-opus-4-7`), so an inherited model can only come from the parent session.

**Observation.**
- The generated config entry is `{"mode":"subagent","description":"…"}`; `"model" in entry` is false; the host's agent record exists (`toBeDefined`) and has `model === undefined`. The host accepts the agent.
- Anthropic: `anthropic/claude-sonnet-5-5#medium` → wire model `claude-sonnet-5-5`, catalog ref `anthropic/claude-sonnet-5-5#medium`, `output_config.effort: "medium"`; `…opus-5-5#xhigh` → `claude-opus-5-5`, effort `xhigh`. `session.get(child).model` equals the per-call `model#variant`.
- OpenAI Responses: `openai/gpt-6-luna#high` → wire model `gpt-6-luna`, top-level `reasoning.effort: "high"`, stored model `openai/gpt-6-luna#high`.
- No per-call model: the child gets the **parent session's model and variant** — stored `anthropic/claude-opus-5-5#medium`, wire model `claude-opus-5-5`, `output_config.effort: "medium"` — and neither the host default `opus-4-7` nor the model of an earlier dispatch (asserted with the root on a model+variant that no step uses). The earlier runs, with the root equal to the host default and then to the first per-call model, could not separate these.

**Design consequence.** A model-less role agent works on both protocols when the dispatch carries `model#variant`, so the router can set the model per call. Without it the child silently runs on the PARENT session's model and variant (at the parent's cost and effort), so P2.1 must still register the floor tier's model on the agent as fallback — this confirms §2.2 / T2.1.1.

## S2 — What `session.get(child)` answers at the first hooks; ordering; overlapping same-title siblings; nonce binding

**Question.** At the child's first `session.hook("context")` and first `permission.hook("evaluate")`, does `session.get(child)` return `parentID`, `agent`, `title`, `model`? How does that relate to the `session.created` event? For siblings of one parent turn that really run at the same time with the same agent, title and prompt, is there anything at the first context hook that tells them apart — in particular a per-dispatch nonce inserted in `execute.before`?

**Method.** Two tests.
- `S2 serialised samples …` (lines 200–272): five children of one model-less agent, all titled `S2 same title`, started one after another (two from different roots, two dispatches flagged `background:true` in successive turns of one root (with enforcement not off the router rewrites them to foreground before the host sees them, asserted from the probe's before record, so they are foreground children), one reader). The probe logs `session.get` at each first hook with a sequence counter and its instance id.
- `S2 siblings spawned by ONE parent turn with their first requests held in flight …` (lines 274–342): the provider answers one parent turn with TWO `subagent` calls in one reply (`SPIKE_CALLS=[…]`), and holds each child's first model request until both have arrived (`holdUntilOverlap`). Two hosts: without and with the probe's nonce (`execute.before` appends ` [nonce <callID>]` to the description and `OMR_NONCE=<callID>` to the prompt).

**Observation.**
- Serialised samples (5 of 5; not a host guarantee): at the first context hook `session.get` returns `{parentID: <its own root>, agent: "role-nomodel", title: "S2 same title", model: {claude-sonnet-5-5, low}}`; at the first evaluate (only the reader has one — a child that calls no tool triggers none) the same fields. The probe saw `session.created` before the first context hook in all five, and both records come from the same probe instance (`__iid` equal), so their sequence numbers are comparable. The event arrives to the probe through a detached loop, so this order is an observation, not a contract. The `session.created` payload carries `parentID`, `agent`, `title`, `model`.
- Overlap: both children's first model requests were in flight at the same time (`arrivals: 2, releasedByArrival: true, timedOut: false`, in both hosts), so the host runs the children of one parent turn concurrently. The full interleaving of the parent's `execute.before` records (`before:i`), `session.created` and first context hooks is recorded in `S2-overlap.json`, not asserted; in both hosts it was `before:0, created:0, context:0, before:1, created:1, context:1`: the second dispatch's `execute.before` ran only after the first child's first context hook, so at that hook exactly ONE dispatch was pending, and at the second child's first context hook the first child was already bound. That is an observation of 2 hosts with 2 siblings, not a contract. What is asserted: the order of the first context hooks equals the order of the parent's `execute.before` records, every child has its `session.created` and context records, and every first-context `session.get` shows `parentID` = the parent root. One probe instance served all records.
- Without a nonce the two siblings are identical at the first context hook: the same `parentID`, `agent`, `title`, `model` and the same first-message text (`You are a subagent spawned by another session.\nS2_HOLD twin`); only the child session id differs.
- With the nonce: each child's `session.get` title at the first context hook is `S2 twin [nonce <its callID>]`, its first context message contains `OMR_NONCE=<its callID>`, the `session.created` payload has the same title, and the map nonce → child equals the map callID → child taken from each call's own `execute.after` result. The nonce was inserted by the probe's `execute.before` hook; the router's own `execute.before` (which already rewrites `args.prompt`) was not used to insert it.

**Design consequence.** The binding of a child to its dispatch is done at the **first context hook**, where `session.get` is proven to answer parentID/agent/title/model; `session.created` is only an early hint (its order relative to the context hook is not a host guarantee). Without a nonce, siblings of one parent with the same agent, title, model and prompt are genuinely ambiguous → keep the intersection fallback of §2.5 (in the observed interleaving only one dispatch was pending at each child's first context hook, so a pending-candidates rule would have been exact there; that ordering is not a contract). The evidence supports a router-inserted per-dispatch nonce (the call id, in the description and prompt of the `subagent` call from `execute.before`) as an exact binding key visible at the first context hook; that the router's own hook can insert it was not run (only the probe did).

## S3 — Per-session narrowing in `evaluate` and `context`; hooks that throw

**Question.** Does the permission `evaluate` hook keyed by `event.sessionID` narrow ONE child only? Can the context hook (`event.tools`) remove tools from ONE session's catalog? What does the host do when a hook throws — and is a throwing `evaluate` really closed for mutating tools?

**Method.** Tests `S3 per-session narrowing …` (lines 514–568) and `S3 edge: a plugin hook that throws …` (lines 570–636). The probe resolves the session title with `session.get(event.sessionID)` and decides per session. In the first test each pair of children has its first model requests held until both are in flight (`holdUntilOverlap`, asserted `arrivals 2, releasedByArrival true, timedOut false` for both pairs), so the pairs really overlap. The second test uses two extra hosts where one hook throws, with a `read`, an `edit` and a `write` child under the throwing title and two children (read, edit) under another title.

**Observation.**
- evaluate: `read` denied for the child titled `S3 A` only → A's tool state `error`, `permission.rejected`, message `PROBE_SESSION_DENIED: read`; B (same agent, overlapping) `completed`. Both parents see a plain `completed` child.
- context: `shell` and `write` removed for `S3 C` only → C's provider request `toolNames` has neither, D's has both; `read`/`edit` untouched in both. A and B (not stripped) still advertise them.
- Throwing evaluate: for `read`, `edit` and `write` the call errors in the child (`errorType: "unknown"`, message `PROBE_HOOK_THROWN evaluate`, `session.tool.failed`); the edited file is byte-identical afterwards and the written file does not exist, so the call is refused, not allowed. The child ends `succeeded` and the parent sees `completed`. The hook stays registered: the next children of the agent under another title are evaluated (the probe logs an evaluate record with the action, decision `pass`) and an edit by one of them goes through (file changed); no host ERROR line.
- Throwing context: the child makes **0 provider requests**; events end `session.execution.failed`, child outcome `failed`; the parent's `subagent` call is `status: error` (`Subagent failed (sessionID: ses_…): PROBE_HOOK_THROWN context`) and the parent's next provider request carries the matching `tool_result` with `is_error: true` and that text; one host log line `level=ERROR … message="Failed to drain Session"` per failed child (three here); no tool ran (edit file identical, write file absent). The next child of the same agent runs fine.

**Design consequence.** Per-session narrowing is available in both hooks. An evaluate error costs one call and does not let it through; a context-hook error kills the whole child. P2.3 must therefore wrap the context hook in try/catch and degrade instead of throwing: the catalog becomes the intersection of `event.tools` with the role's floor grant (never adding an action; empty for a role with no local grant) and the degradation is annotated for the parent in `execute.after` — otherwise a visible failure is replaced by a silently reduced child. The evaluate hook should catch and return an explicit deny with a clear message (as the router does for protected agents, `v2-hooks.ts:307-309`) rather than rely on the generic `unknown` error.

## S4 — How the parent sees a step-limit stop and a plugin-guard denial

**Question.** What does the PARENT model receive when the child hits its agent `steps` limit, or when a plugin guard denies its tool call? What does the host do on the child side?

**Method.** Test `S4 how the parent sees a child that hits its step limit …` (lines 344–429). Agents with `steps: 2` and `steps: 3`, a second agent denied `read` by the probe's `evaluate` hook, a control agent. The scripted provider either answers with text on the last step, or keeps calling a tool (`loopProbe`, which ignores `tool_choice: none`). What the parent saw is taken from the `tool_result` of the parent's NEXT provider request (`host.requestsOf(root)` first `primary` request with `toolResult`), not from the probe's `execute.after` record.

**Observation.**
- Parent side (asserted on the parent's next request): the tool_result is EXACTLY the host envelope `<subagent sessionID="ses_…" state="completed">\n<text>\n</subagent>` with `<text>` = `CHILD_OK` (scripted child that answers on its last step), `Subagent completed without a text response.` (scripted child that only calls tools) or `ROOT_DONE` (scripted fixed reply after a denied call). Nothing else: no step, budget or denial wording.
- Child side, `steps: 2`: request 1 is a normal tool step; request 2 (the last allowed step) carries the host's `MAXIMUM STEPS REACHED` note and `tool_choice: {type: "none"}`. If the scripted model answers with text the child ends `succeeded` (finishes `tool-calls`, `stop`). If it calls a tool anyway (possible only with a provider that ignores `tool_choice`), the host answers that call with an error to the child model — `Tools are disabled after the maximum agent steps`, `session.tool.failed` — and the session ends `succeeded` with finish `tool-calls` and no text.
- `steps: 3` with the looping scripted model: requests `[tool, tool, tool+maxSteps/tool_choice none]`, tool states `[completed, completed, error "Tools are disabled after the maximum agent steps"]`. So for N = 2 and N = 3 a limit of N gives N−1 tool-capable steps and one final tool-less step (only these two values were run).
- Guard denial: the child's tool state is `error`, type `permission.rejected`, message `PLUGIN_GUARD_DENIED: read`; the tool hook records `Permission.BlockedError`; the session goes on and ends `succeeded` (the continuation text is the scripted fixed reply, not evidence of host recovery behaviour).

**Design consequence.** Neither the step limit nor a guard denial reaches the parent in its tool result; the signals exist only on the child side (`session.tool.failed`, `Permission.BlockedError`, the max-steps note in the child's request), where only plugin hooks can see them. Budget exhaustion and authority denials must therefore be annotated by the plugin (`execute.after`, S6) from plugin-side state (P1.5 `budgetExhausted`). The host `steps` limit must sit ABOVE the role budget so the plugin's "NEED MORE: budget" message fires first — amend T2.1.1 "steps from the top budget" to `steps = top budget + margin` (N means N−1 tool steps, observed for N = 2 and 3).

## S5 — Where the inferred acceptance criterion is cut (code reading, no host run)

**Question.** Why can a `NOT ACCEPTED` criterion be a truncated first line of the dispatch, and does the same `args` object mutated by the dispatch header reach the DoD builder?

**Method.** Code reading, no test: `src\verify\dod.ts`, `src\verify\dispatch.ts`, `src\router\dispatch-header.ts`, `src\index.ts`, `src\compat\v2-hooks.ts`.

**Observation.**
- Cut site: `summarizeDispatch` (`src\verify\dod.ts:57-65`) returns `trimmed.slice(0, 120)` of the **first non-empty line** (`:62`). `inferDoD` pushes that summary as the sole criterion when no deterministic check applies (`dod.ts:254-260`).
- `buildDelegationDoD` (`src\verify\dispatch.ts:552-561`): no `[acceptance]` block → `inferDoD(args.prompt ?? args.description, "", hints)`.
- Header: `src\index.ts:1732-1734` prepends `buildDispatchHeader(...)` (`src\router\dispatch-header.ts:14-35`) to `args.prompt` as `<header>\n\n---\n\n<original prompt>`. The header is several paragraphs: the first is `[router] You are @<tier>. Execute this dispatch yourself; do not route it to another tier, and do not ask to be re-dispatched.`, then `Working directory: …`, the tool-name paragraph, the empty-result paragraph, the budget paragraph, `CAP:<n>`, the budget-change sentence and the false-refusal sentence. The after hook reads the dispatch at `src\index.ts:1883-1886`, so for a header-prefixed prompt the inferred criterion is the header's first 120 characters.
- **Not the same object on v2.** `taskArgs` copies the input (`src\compat\v2-hooks.ts:47-50`); the before-hook mutation at `index.ts:1734` lands on that copy; the compat layer writes it back with `event.input = nativeArgs(...)` (`v2-hooks.ts:528`) and the after hook re-reads it through a new copy (`scopedArgs(event)`, `v2-hooks.ts:584`). In between, the text the router ADDED is passed through `translateAdded(prompt, output.args.prompt)` (`v2-hooks.ts:524-527`, defined at `:79-86`), which runs the added part through `v2Instructions` (`:27-35`: `Task(`→`subagent`, `Task call(s)`/`Task tool`/`task tool`/`` `task` ``→`subagent …`, `subagent_type`→`agent`, `task_id`→`sessionID`). The current header text contains none of those words, so the v1 and the v2-translated header are byte-equal today, but a later header edit would make them differ; nothing in the code guarantees equality.
- The header is only added when the agent is an active tier (`index.ts:1718-1724`: `Object.prototype.hasOwnProperty.call(getActiveTiers(cfg), tier)`) and the prompt does not already start with `[router] You are @`. A dispatch to a non-tier role agent gets **no** header.
- Rendering of `NOT ACCEPTED`: `buildForcingNote` (`src\verify\dispatch.ts:598-613`, text at `:613`) contains no truncation; the 120-character cut happens earlier, in the criterion.

**Design consequence.** The cut site is confirmed. P1.5's ownership gains `D:\git\opencode-model-router\src\verify\dispatch.ts`: inside `buildDelegationDoD`, when the prompt starts with `[router] You are @`, drop everything up to and including the FIRST `\n\n---\n\n` before parsing/inferring (stripping only the first line would leave `Working directory: …` as the criterion). Tests in P1.5 must cover the v1 form and the v2-translated form (`translateAdded`). `src\index.ts` (Wave-2 hot file) need not change in Wave 1. The defect only affects tier dispatches; role-agent dispatches have no header (but still get a 120-character first-line criterion when no check applies).

## S6 — `execute.after` on the parent's `subagent` call

**Question.** Can `tool.hook("execute.after")` on the parent's `subagent` call append text that the PARENT model sees? In what order against the router's own after-hook? What happens to a dispatch flagged `background: true`?

**Method.** Tests `S6 tool.hook execute.after … appends text the PARENT model sees …` (lines 638–664) and `S6 order against the router's own after-hook, and a background-flagged dispatch with verification on and off` (lines 666–734). The probe appends a note to the completed result; assertions are on the parent's next provider request (the `tool_result` block matched by `tool_use_id`). The second test runs twice, with enforcement `enforced` and `off`: once foreground with an `[acceptance]` fileExists check, once flagged `background: true` with the child's first request held for 4 s. The probe loads after the router, so its `execute.before` record shows the input the router left for the host.

**Observation.**
- The parent's next request carries exactly one `tool_result` block with exactly two text parts: the host envelope `<subagent sessionID="ses_…" state="completed">\nCHILD_OK\n</subagent>` and then the note. The child's own requests never contain the note. (The probe's own earlier `execute.after` record shows the result before the append, so it is not evidence; the provider request is.)
- Order: with the router's verification on, the parent's tool_result parts are `[envelope, "\n\n[router ✓ verified: deterministic]", note]` — the router plugin (loaded first) appends before the probe plugin (loaded second). This is plugin load order observed once on the host's output; it was not tested with several hooks of one plugin (the S9 observation that an earlier-registered hook of the same plugin saw the original input is the only within-plugin order evidence).
- Background, verification ON (`enforcement.mode: "enforced"`): the model sent `background: true`, but the probe's `execute.before` record shows `background: false` — the router flags every task call as verifying when the mode is not off and `verify.require` is not `never` (`src\index.ts:1663-1665`) and the compat layer writes `background:false` (`v2-hooks.ts:513/:528/:60`). The host therefore received a foreground call: it stayed open for the held child (≥ 3.5 s), returned `state="completed"`, and the router's verification line and the probe's note were both appended. This says nothing about the host's own background behaviour.
- Background, verification OFF (`mode: "off"`): the call reaches the host with `background: true` (probe record). The host answers within a few ms (< 3 s asserted, 47 ms observed) with a running acknowledgement (`status: "running"`, text `The subagent is working in the background (sessionID: ses_…)`) that the probe's `execute.after` extended with its note; exactly ONE `execute.after` record exists for the call. When the child finishes, its final text reaches the parent in a later host-made user message `<subagent sessionID="…" state="completed" description="S6B bg">\nCHILD_OK\n</subagent>` — not a tool_result, not passed through `execute.after`, and carrying no appended note.

**Design consequence.** Confirmed: plugin-side annotations (budget, authority, verification) appended in `execute.after` reach the parent model; this is the delivery channel for S4's missing signals. For a background dispatch (reached only when verification is off) the channel covers the running acknowledgement only: the final result is delivered by the host outside `execute.after`. By code reading the router's own after-hook has the same limit (`v2-hooks.ts:543` returns for a non-completed status, `:562-577` appends notices only to a running ack). The router already forces foreground for every subagent call whenever verification is active; roles mode extends that to role dispatches when verification is off or `require` is `never` (P-5), through the same `nativeArgs` path (`v2-hooks.ts:60`). Only `mode: "off"` was run; `require: "never"` rests on the code reading of `index.ts:1663-1665`.

## S7 — Resuming a child with another model/variant

**Question.** When the parent resumes a child (`subagent` with the child's `sessionID`) with a different per-call model and variant, which model/effort reach the provider? Is it the same child, with its history, if resumed twice or across providers?

**Method.** Test `S7 resuming a child with a different per-call model and variant (twice) …` (lines 430–512). The child id of every call is taken from that call's own result (a resume must name the same child; the input is not echoed back).

**Observation.**
- Anthropic: `sonnet#low` → resume `opus#xhigh` → resume `sonnet#medium`: wire models `claude-sonnet-5-5`/`claude-opus-5-5`/`claude-sonnet-5-5`, efforts `low`/`xhigh`/`medium`; `session.get` model follows each time.
- OpenAI Responses: `luna#low` → `sol#high` → `luna#max`: wire models `gpt-6-luna`/`gpt-6-sol`/`gpt-6-luna`, efforts `low`/`high`/`max`.
- Cross-provider: an Anthropic child resumed on `openai/gpt-6-luna#high` moves to the Responses protocol at effort `high`.
- Identity: every resume's result names the resumed child (`call.childID === sessionID`); the root has exactly one child per start.
- History (asserted on the resumed request's messages as the provider received them): the resumed request contains the earlier prompts (`S7 anthropic start sonnet#low`, then also `… resume 1 opus#xhigh` on the second resume; the `responses` and `cross` equivalents) and at least one earlier `CHILD_OK` reply (two after two earlier turns); the new child `x0`, created after the others, contains none of the `S7 anthropic …` / `S7 responses …` prompts of the earlier children.
- When the model changes with the resume the new effort is the top-level one (no in-band configuration change), on both protocols.

**Design consequence.** Confirmed: a role can be resumed on a higher tier (and even another provider) with the same child session, keeping its earlier turns. In-band effort changes were not exercised here (the model changed on each resume); the older same-model scenario (`routing-engine.smoke.test.ts`, scenario 7) covers them.

## S8 — Code Mode `execute`: permission evaluation and catalog filtering

**Question.** Are inner `tools.*` calls made inside `execute` evaluated by `permission.hook("evaluate")`? Can the per-session `context` hook restrict the Code Mode catalog to an allowlist? What about an inner call outside the allowlist? Can `execute` be removed from a role agent?

**Method.** Test `S8 Code Mode execute …` (lines 736–790); an exploratory run first (`S8x.json`). The child calls `execute` with scripted code. The removal of `execute` from role agents is exercised in S11 (section 12; lines 919–1112).

**Observation.**
- Code Mode is on by default in the isolated host (`execute` advertised and runs). The inner catalog is NOT the agent's tool list: namespaces `["opencode","browser"]`; `opencode` = `session_rename, session_move, models, list_mcp_resources, read_mcp_resource`; `browser` = 30 operations, listed but not callable (`Tool 'browser.tabs' is not callable.`). Native tools such as `read`/`shell` are not in it. Inner `search()` (a global) searches that catalog.
- **No** `evaluate` event fires for the `execute` call itself, for inner `models`, for inner `session_rename`, for the browser call or for `search`. A native `read` of a control child does fire one.
- Inner `tools.opencode.session_rename({title})` really renamed the child's session on the host (`session.get(...).title === "S8 renamed by execute"`).
- The context hook can cut the agent-level catalog to exactly `["subagent","execute"]` (provider request `toolNames`), but `event.tools` has no inner entries: the inner namespaces, the five `opencode` operations and `search` are unchanged, and an inner call outside the allowlist (`session_rename` in the filtered session) still ran and changed the title.
- Catalog absence is the only control (S11, section 12): `execute` is advertised to the host-default agent and absent for a deny-by-default agent, for a deny-by-default researcher and for an otherwise default agent with an explicit `execute: deny`; a call to it fails with `No tool named "execute" is currently available…` and the scripted inner `session_rename` does not run (the child's title is unchanged); no `evaluate` event fires.

**Design consequence.** Code Mode inner calls are never evaluated and the inner catalog cannot be filtered by the context hook, so the only control is whether `execute` is in the agent's catalog. `execute` must be **denied to every role agent in roles mode** (omitted from the floor grant; `execute: deny` for any otherwise allowing agent); the researcher keeps `webfetch`, `websearch` and `context7_*` (see P-6) and no Code Mode; `codeModeAllow` is dropped from `RoleSpec`/`roleAgents` (amend §2.2, §2.4, T1.1.2, T1.1.3). The inner catalog seen here is specific to the isolated host: in production MCP servers and a connected browser join it, tier agents keep `execute`, and `session_move` changes a session's directory (it may take an optional `sessionID`; not verified on 2.0.24) — that directory feeds `router_git_*` (`v2-hooks.ts:357`) and relative-path resolution. P1.3 and P2.3 therefore take the work root from the router's binding, never from `session.location`.

## S9 — Rewriting `args.agent` in `execute.before`

**Question.** If `tool.hook("execute.before")` of the `subagent` call rewrites `agent: "explore"` to `"explorer"` (a registered custom agent), which agent does the child actually run as — and is the rewritten agent's permission policy enforced?

**Method.** Test `S9 rewriting args.agent explore -> explorer …` (lines 792–856). The probe assigns `e.input = {...e.input, agent: "explorer"}`; the custom agent (host `opencode.json`) has a marker system prompt and an `edit` deny. Besides the plain child, the rewritten child ATTEMPTS an edit from a root session with no inherited grants and from a root session with an allow-all grant; a control agent attempts the same edit.

**Observation.**
- `session.get(child).agent === "explorer"`, the `session.created` payload and the first context hook carry `explorer`, and the provider request's system prompt starts with the custom marker (a control child has none). A probe `execute.before` hook registered earlier in the same plugin still saw `agent: "explore"`.

- Enforcement, parent session with an allow-all grant (`newRoot`'s default): the rewritten child's request DOES advertise `edit`, the edit completes and the file changes — the host-defined agent's `edit: deny` is not enforced. ## S10 — Is the verification gate specific to tier agents?

**Question.** Does the router's verification gate run the acceptance checks for a child dispatched to a non-tier custom agent, compared with `fast`/`medium`? What decides whether a dispatch is gated?

**Method.** Test `S10 the router's verification gate treats a non-tier custom agent exactly like fast/medium …` (lines 859–916). Four hosts (enforcement `enforced`, default, `off`, `verify.require: "never"`); each foreground dispatch carries `[acceptance]\ncheck: fileExists path=<abs>\n[/acceptance]` with one existing and one absent file. The verdict is read from the dispatch result and from the tool_result of the parent's next provider request. A background-flagged dispatch is covered in S6: with verification on the router forces it to foreground before the host sees it.

**Observation.**
- `enforced`: for `fast`, `medium`, `explorer`, `implementer` alike, file present → result text `CHILD_OK\n\n[router ✓ verified: deterministic]`; file absent → `[router ⚠ NOT ACCEPTED] The delegated result was not accepted by independent verification:\n- file not found: …\ns10-absent.txt`. The same lines are in the tool_result of the parent's next provider request (asserted for every agent and both outcomes). The deterministic checker ran; the grader count stayed 0.
- The only difference is the next-step hint: `fast`/`medium` get ``re-run via `subagent(agent="medium")` (escalated from fast)`` (and `heavy` for medium); `explorer`/`implementer` get `NEXT: address the above and re-run the delegation; do not treat the prior result as complete.`
- The default (advisory) mode gates as well; `enforcement.mode: "off"` and `verify.require: "never"` leave the plain `CHILD_OK`.
- What decides gating: `shouldVerifyTask` (`src\verify\dispatch.ts:580-589`) checks only `tool === "task"` (`:585`), `mode !== "off"` (`:586`) and `require !== "never"` (`:587`); it is called at `src\index.ts:1874` after `resolveEnforcementMode` (`:1869`; v2's `subagent` is mapped to `task` by `legacyToolName`, `src\compat\v2-hooks.ts:70`). Around it: the hook returns when the router is bypassed (`index.ts:1797`), the compat layer runs it only for a completed result (`v2-hooks.ts:543`) and gives a running ack only notices (`:562-577`). There is no agent-name list or tier lookup. The producer name only feeds the hint: `ladder.indexOf(producerTier)` (`src\index.ts:2023-2026`); a name outside `escalate.ladder` gives `nextTier = null`.

**Design consequence.** The gate is agent-agnostic. Effective detection is deterministic when ALL hold: the call is `task`/`subagent`; `enforcement.mode ≠ off`; `verify.require ≠ never`; the router is not bypassed; the return is a completed foreground result; and the dispatch carries a deterministic check. Without one, the inferred criterion goes to the checker/grader path: `buildDelegationDoD` is called without hints (`index.ts:1668`, `:1883`), so `inferDoD` adds no checks (`dod.ts:229-249`) and the DoD kind is `checker` (`dod.ts:266-267`). Role agents work with no extra wiring but get only the generic escalation hint, so P2.1 must add a role-aware hint (resume the same child on a higher tier, see S7).

## S11 — Work root in a sibling worktree

**Question.** From a session in the main checkout, can a deny-by-default role agent read, edit and call a plugin tool on a sibling `git worktree`? Is `external_directory` asked or denied by default; can the agent's max policy allow only the listed worktree root; how far does a glob grant reach; where does a plugin tool run; is a worktree created after the host started covered; which tools does the catalog expose to role agents; is the grant the same for agents registered by the router?

**Method.** Two tests, stating the registration path of each.
- `S11 work root in a sibling worktree (agents defined in the HOST's opencode.json) …` (lines 919–1112): a git repo in the temp root (main checkout = host project, `wt-1` sibling worktree with a nested `sub\deep\n.txt`, an unrelated `other`, a plain `wt-evil` directory that matches the glob, `wt-2` created after the host started). Agents come from the host's `opencode.json` `agents`: `role-base` (host defaults), `role-deny` (`"*": deny` + read/edit/`wt_probe`/`router_git_status` allows), `role-wt1` (`+ external_directory <root>\wt-1\*`), `role-glob` (`<root>\wt-*`), `role-case` (the rule in upper case), `role-long` (the rule in the long, non-8.3 spelling of the root), `role-notool` (`"*": deny` + `read`), `role-exec-deny` (defaults + `execute: deny`), `role-research` (`"*": deny` + read/webfetch/websearch). The probe turns an `ask` into a deny to avoid hangs and logs `effectIn` (positional: the lifecycle record is written before the session-keyed hook runs).
- `S11 repeated with agents defined in the ROUTER override …` (lines 1114–1189): the same worktree layout with agents `r-deny`, `r-wt1`, `r-glob` registered through the router override (`agents.<name>.permission` maps). Root sessions are created with no inherited grants unless stated.

**Observation (host-defined agents).**
- Default agent: `external_directory` is **asked** (`effectIn: "ask"`, resource `<root>/wt-1/*`) for read and edit.
- `role-deny` (no `external_directory` rule): refused by the host itself — `Permission denied: external_directory`, no `evaluate` event reaches plugins; the refused edits (their own file `e0.txt`) left it unchanged.
- `role-wt1` (rule for the worktree root only): read and edit run (evaluate sequence `external_directory allow`, then `read`/`edit allow`); the edit is on disk in `wt-1` and not in the main checkout. A nested file below the root is covered. Read AND edit of a path in `other` are refused (`Permission denied: external_directory`) and `other\x.txt` is unchanged. `wt-evil` and `wt-1\..\other\x.txt` are refused (`..` is normalised before matching).
- `role-glob` (`<root>\wt-*`): covers `wt-1` (read, edit, nested) and **also the plain directory `wt-evil`** (over-match: `*` crosses separators and matches any prefix); `other` read and edit refused. A worktree `wt-2` created AFTER the host started is **denied** with no pattern (`role-deny`) and with the exact `wt-1` pattern; **covered** (read and edit) by the glob registered at start.
- Spelling: on win32 a rule written in upper case grants the path (case folding is win32-only, `src\router\read-only.ts:27`); when the temp root has an 8.3 component, a rule in the long spelling does not grant a path given in the 8.3 spelling and a rule in the 8.3 spelling does not grant a path given in the long spelling (both refused). The test asserts these only where applicable (win32 / an 8.3 component in the temp root) and records `S11-applicability.json`.
- Session grant (section 10 of the test): the same `role-deny` agent reads the sibling worktree when the parent session grants everything (`newRoot`'s default) — the session-level grant decides before the agent's policy — and is refused when the parent grants nothing. Under that allow-all parent the host also advertises it the FULL catalog, including tools its policy does not list (`execute`, `shell`, `subagent`, `wt_probe`).
- Plugin tool: runs with `process.cwd()` = the main checkout (= session location = plugin location); its context keys are only `sessionID, agent, messageID, id, progress, signal`. No `evaluate` fires for it, even with a sibling path argument. (a) Under deny-by-default WITHOUT an explicit allow (`role-notool`) the host does not advertise `wt_probe` and a call fails with `No tool named "wt_probe" is currently available…` (`tool.execution`), it never runs, no `evaluate`. With the allow it is advertised and runs. (b) When the max policy allows `external_directory`, the plugin `evaluate` hook **does fire** (`effectIn: "allow"`) and can narrow it for one session (`PROBE_SESSION_DENIED: external_directory` for the session titled `S11 role-wt1 narrowed`; the same agent's other children read the path).
- `router_git_status` called by the `role-wt1` child (session in the main checkout) reports the MAIN checkout's untracked file (`main-only-dirty.txt`) and not `wt-1`'s `sub` directory: the compat wrapper resolves it against the session location (`v2-hooks.ts:356-358`) while it passes `directory = ctx.location.directory` and `worktree = project directory` to other router tools (`:359-361`).
- Catalog: `execute` is advertised to `role-base` and absent for `role-deny`, `role-notool`, `role-research` and for `role-exec-deny` (explicit `execute: deny`); a call fails with `No tool named "execute" is currently available…`, the scripted inner `session_rename` does not run (title unchanged) and no `evaluate` fires. `webfetch` and `websearch` are advertised natively to `role-base`, kept by explicit allows under deny-by-default (`role-research` catalog is exactly `[read, webfetch, websearch]`) and absent without them. No `context7_*`/`brave_*` tool is advertised by the isolated host (no MCP configured).

**Observation (router-registered agents).** The router-override test covers: deny without a rule, the exact rule (read, edit), `other` (read, edit), `wt-evil` (exact rule refuses, glob over-matches), the glob, `wt-2` created later (glob only) — each as for host-defined agents — and, under a parent session that grants everything, (a) the missing `external_directory` rule, refused by the router's own `evaluate` hook (`Permission denied by plugin agent r-deny: external_directory`; the probe already receives the event as a deny, `effectIn: "deny"`), and (b) the CATALOG: the router-registered agent's tool list is exactly `[edit, read, write]` — `execute`, `subagent` and the plugin tool `wt_probe` are not advertised although the parent grants everything and the host advertised them to the host-defined agent in the same situation — and calls to `execute` and `wt_probe` fail with `Tool is not available for this request: <name>` without running (the inner `session_rename` did not rename the session; no plugin-tool report was recorded). The stripping is done by the router's context hook (`src\compat\v2-hooks.ts:395-411`, which empties the catalog on error). Not covered for router-registered agents: nested paths, `..`, letter case, 8.3/long spelling, plugin-tool execution with an explicit allow, `router_git_status`, the execute/webfetch catalog under a parent without grants, per-session narrowing. No router warning or host error was logged.

**Design consequence.** Max-policy `external_directory` rules for the listed worktree roots work and a worktree created later needs a glob, which confirms `routing.workRoots`. The glob over-matches: `<root>\wt-*` grants every sibling beginning with `wt-`, nested paths and a non-worktree directory, and a production glob such as `D:\git\omr-rta-*` would grant every role child every worktree, so the max policy cannot separate dispatches — per-session narrowing in `evaluate` is mandatory, allowing only the session's bound work root and denying everything else (unknown or absent binding → deny). Matching is case-insensitive on Windows but spelling-sensitive for the 8.3/long form, and the host decides before any plugin runs (a refused path produces no `evaluate` event), so the router cannot repair a spelling afterwards: it registers the canonical long form only (`realpathSync.native`; Node has no 8.3 short-name API and 8.3 can be disabled per volume), the P1.1 validator expands or rejects 8.3 components, the child is only ever given that spelling (dispatch header, binding, `router_run` cwd) and any other spelling is refused — fails closed. Per-session narrowing uses the same canonical form and matcher (`read-only.ts:24-28`). Without a rule the host refuses before plugins see anything. A native plugin tool gets no directory in its context, while the router's own tools get `directory` = the main checkout through the compat wrapper (`v2-hooks.ts:359-361`); `router_git_*` follows the session location, and no `evaluate` fires for plugin-tool execution: `router_run` and `router_git_*` must take the work root from the router's binding (never from `context.directory`, `context.worktree` or `session.location`), validate it themselves and refuse when there is no binding. The agent's policy only decides whether a plugin tool is available at all. Finally, under a parent session that grants everything the host does not enforce a host-defined agent's policy (permissions and catalog), while for a router-registered agent the router's own hooks do (`evaluate` for permissions, the context hook for the catalog, `v2-hooks.ts:289-311` / `:395-411`); P-19.

## S12 — Changing the override's `agents` block without a restart

**Question.** If the router override's `agents` block changes while the host runs (description, new agent, tightened permission, removed agent), when do `GET /api/agent`/`client.agent.list()`, the orchestrator's `subagent` catalog and the children's catalogs follow?

The second host registers `worker` (read+edit) and `doomed`, then rewrites the override with `worker` edit denied, `doomed` removed and `newbie` added, and dispatches from a root without inherited grants.

**Observation.**
- Before: all three views show `reviewer … description ONE`. Immediately after the write, and during the 30 s poll, nothing changes (`changedByItselfAfterMs` undefined).
- (A) The **first ordinary prompt** after the change already carries the new catalog in its own provider request (`description TWO`, agent `newbie`), and `agent.list` and `/api/agent` show both; the state stays on the next prompt.
- (B) `/router-reload` alone (no ordinary prompt) also brings `agent.list` and `/api/agent` to the new block (only these two list views were checked after the command).
- Beyond a description: after the change the agent list changes only at the next dispatch/prompt (`[doomed, worker]` immediately after the write, `[newbie, worker]` after it); a FRESH `worker` child has no `edit` tool in its request and its edit is refused with the file untouched; the OLD `worker` child, resumed after the change, keeps its history (the first edit stays `completed`) but its new request has no `edit` tool and the new edit is refused (file untouched); the new agent `newbie` is dispatched at once (child agent `newbie`, its edit applied); dispatching the removed `doomed` fails with `Tool.Error: Unknown agent: doomed` and no child is created.
- Scope: router-defined agents (the override's `agents` block). Agents defined in the host's `opencode.json` were not changed during the run.

**Design consequence.** An `agents` change in the router override (description, new agent, tightened permission, removed agent; loosening a permission was not tested) is live on the next prompt without a restart (`/router-reload` was checked for the agent list views only) and also binds resumed children, so DF-2b is not needed for router-defined agents (amend §0.7, DF-2 step 3, handover §7). Keep DF-2b only for agents defined in the host's `opencode.json`, which this spike did not exercise.
